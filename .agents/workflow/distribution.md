# Distribute published GitHub tickets

Run this after `/to-tickets` publishes a batch. The configured roster contains human owners, not agent names. An owner chooses their Codex, Cursor, Claude Code, or another authorized harness.

1. Check `.agents/team.json`. If absent, copy `.agents/team.example.json` and ask for the actual GitHub repository and current participating members. Each member has a GitHub login, positive `capacity` (relative planning weight), and skills. Include `general` if the member can take general tasks. Capacity is not a hard concurrency limit. Do not infer the roster from all repository collaborators.
2. Check that the target repository matches the intended project and that `gh auth status` succeeds. Every named member must be assignable in that repository. If the tracker is not GitHub, do not run this GitHub-specific step; report that an adapter is required.
3. Write a UTF-8 JSON manifest for this batch, e.g. `.scratch/<feature>/assignment-manifest.json`, with the exact published issue numbers. See `.agents/workflow/tickets.example.json`. `blocked_by` contains issue numbers, including blockers outside the batch; an omitted blocker is treated as no blocker, so transcribe every edge. Set `skills` to the required capabilities, or `[]` for no restriction. Set a positive numeric `estimate`, default 1 when unknown. Never invent evidence for skills, assignees, or estimates.
4. From the repo root run `python .agents/workflow/distribute.py --team .agents/team.json --tickets <manifest> --apply`. This fetches current issue and blocker state, checks every roster login, plans deterministically, and assigns only currently unassigned open issues. `--apply` is the automatic distribution step; omit it to preview. Treat an issue's current assignee as authoritative and never remove or replace them.
5. Review the JSON report and verify the `applied` entries. Report each assignment, blocked issue, unassignable issue, skipped item, and failure to the user. If any write fails, report partial completion and retry only after resolving it; rerunning is safe for already assigned issues. Do not claim an agent has started, a PR exists, or an issue is ready when its blockers are open.

The algorithm considers only the current batch and its blockers, not the team's workload elsewhere. It assigns blocked issues to owners for planning, but their implementation must wait for blockers to close. It requires every requested skill to appear in the member's list; `general` is an ordinary skill, not a wildcard. When no eligible person exists the issue remains unassigned. Existing assignees are counted toward their roster member's load where possible. Assignment is not a transactional reservation: concurrent tools can race, so verify results and coordinate a single dispatcher per batch.

`--apply` changes issue assignees; it does not start agents, create PRs, create project items, alter statuses or notify people through custom messages. The tracker setup may separately add newly created issues to a GitHub Project. Do not add an issue to a different board by guessing its identity.
